M 01

Grain — What Does One Row Actually Mean?

The root cause of most incorrect marketing numbers
User Journey
A person sees a Facebook ad → clicks it → lands on a product page → fills a lead form → gets called by sales → buys. One journey. Multiple tables. Multiple grains.
The Data Trail — Four Tables, Four Grains

Every action the user takes lands in a different table at a different grain. The key is understanding each table represents the same person at different points in their journey.

Data Tables — One Journey, Four Grains
-- impression_events  (grain = one ad impression)
user_id │ timestamp               │ campaign_id │ channel
u_001   │ 2025-01-10 09:14:22 UTC │ camp_77     │ facebook
u_001   │ 2025-01-10 11:02:01 UTC │ camp_77     │ facebook   ← same user, 2nd impression
-- 14 total impressions for u_001 on camp_77

-- click_events  (grain = one click)
user_id │ timestamp               │ campaign_id │ landing_page
u_001   │ 2025-01-10 09:14:35 UTC │ camp_77     │ /products/shoes

-- lead_events  (grain = one form submit)
user_id │ timestamp               │ form_id  │ campaign_id
u_001   │ 2025-01-10 09:17:01 UTC │ form_12  │ camp_77

-- deals  (grain = one closed deal)
user_id │ close_date  │ revenue │ campaign_id
u_001   │ 2025-01-28  │ £249    │ camp_77
⚠ The Trap
If you JOIN impression_events directly to deals, u_001's 14 impressions multiply against £249 revenue. Your pipeline reports £3,486 instead of £249. SQL runs without error. The number is completely wrong.
❌ The Broken Join
WRONG — Direct join across incompatible grains
SELECT
    i.user_id,
    i.campaign_id,
    SUM(d.revenue)  AS revenue  ← £249 × 14 impressions = £3,486
FROM impression_events i
LEFT JOIN deals d
    ON i.user_id     = d.user_id
    AND i.campaign_id = d.campaign_id
GROUP BY 1, 2
Result — Silently Wrong
user_id │ campaign_id │ revenue
u_001   │ camp_77     │ 3,486.00   ← should be £249
✅ Fix 1 — Aggregate to Matching Grain First

Resolve each table to user_id + campaign_id grain in a CTE, then join them. Both sides of the join now have exactly one row per user per campaign.

CORRECT — Deduplicate before joining
WITH user_impressions AS (
    SELECT
        user_id,
        campaign_id,
        COUNT(*)        AS impression_count,
        MIN(timestamp)  AS first_seen_at,
        MAX(timestamp)  AS last_seen_at
    FROM impression_events
    GROUP BY user_id, campaign_id  ← grain = one row per user+campaign
),

user_deals AS (
    SELECT
        user_id,
        campaign_id,
        SUM(revenue)    AS total_revenue,
        COUNT(*)        AS deal_count
    FROM deals
    GROUP BY user_id, campaign_id  ← same grain — safe to join
)

SELECT
    ui.campaign_id,
    COUNT(DISTINCT ui.user_id)      AS reached_users,
    SUM(ui.impression_count)         AS total_impressions,
    SUM(ud.total_revenue)            AS revenue,
    SUM(ud.deal_count)               AS deals
FROM user_impressions ui
LEFT JOIN user_deals ud
    ON ui.user_id     = ud.user_id
    AND ui.campaign_id = ud.campaign_id
GROUP BY ui.campaign_id
Result — Correct
campaign_id │ reached_users │ total_impressions │ revenue │ deals
camp_77     │ 3,847         │ 51,203            │ 5,478   │ 22
✅ Fix 2 — Build Stable Intermediate Tables at Pipeline Time

Never recompute grain resolution in dashboard queries. Build these once in your pipeline.

Pipeline models — pre-aggregated fact tables
-- fact_daily_channel: one row per day per channel
CREATE TABLE fact_daily_channel AS
SELECT
    DATE(timestamp)             AS report_date,
    channel,
    COUNT(*)                    AS impressions,
    COUNT(DISTINCT session_id)  AS sessions,
    SUM(spend)                  AS spend
FROM impression_events
GROUP BY 1, 2;

-- fact_leads_daily: one row per day per campaign
CREATE TABLE fact_leads_daily AS
SELECT
    DATE(submitted_at)          AS report_date,
    campaign_id,
    COUNT(*)                    AS leads,
    COUNT(DISTINCT user_id)     AS unique_leads
FROM lead_events
WHERE is_test = FALSE         ← exclusion rule documented here
  AND is_bot  = FALSE
GROUP BY 1, 2;
✅ Fix 3 — Multi-Grain Rollup Across Fact Tables
WRONG — Joining all raw tables in one query
SELECT
    DATE(i.timestamp), i.campaign_id,
    COUNT(i.event_id)  AS impressions,
    COUNT(l.lead_id)   AS leads,    ← multiplied by impression rows
    SUM(d.revenue)     AS revenue   ← multiplied further
FROM impression_events i
LEFT JOIN lead_events l ON i.user_id = l.user_id AND i.campaign_id = l.campaign_id
LEFT JOIN deals d       ON i.user_id = d.user_id AND i.campaign_id = d.campaign_id
GROUP BY 1, 2
CORRECT — Join pre-aggregated fact tables at matching grain
WITH daily_impressions AS (
    SELECT report_date, campaign_id, impressions, spend
    FROM fact_daily_campaign          ← already day+campaign grain
),
daily_leads AS (
    SELECT report_date, campaign_id, leads
    FROM fact_leads_daily             ← already day+campaign grain
),
daily_revenue AS (
    -- Revenue joins on close_date, not campaign run date
    -- This is the attribution window decision made explicit in SQL
    SELECT
        DATE(close_date)  AS report_date,
        campaign_id,
        SUM(revenue)      AS revenue,
        COUNT(*)          AS deals_closed
    FROM deals
    GROUP BY 1, 2
)

SELECT
    di.report_date,
    di.campaign_id,
    di.impressions,
    di.spend,
    COALESCE(dl.leads,           0) AS leads,
    COALESCE(dr.revenue,         0) AS revenue,
    COALESCE(dr.deals_closed,    0) AS deals,
    SAFE_DIVIDE(di.spend, dl.leads)      AS cpl,
    SAFE_DIVIDE(dr.revenue, di.spend)    AS roas
FROM daily_impressions di
LEFT JOIN daily_leads   dl ON di.report_date = dl.report_date AND di.campaign_id = dl.campaign_id
LEFT JOIN daily_revenue dr ON di.report_date = dr.report_date AND di.campaign_id = dr.campaign_id
ORDER BY di.report_date DESC
Result — Revenue lag is now visible in the data
report_date │ campaign_id │ spend  │ leads │ revenue │ cpl   │ roas
2025-01-10  │ camp_77     │ 384.00 │ 27    │ 0.00    │ 14.22 │ 0.00
2025-01-11  │ camp_77     │ 356.00 │ 31    │ 249.00  │ 11.48 │ 0.70
2025-01-28  │ camp_77     │ 0.00   │ 0     │ 1,247   │ null  │ null
                                            ↑ deals from Jan 10 leads close here — 18-day lag
✅ Fix 4 — Deduplication with ROW_NUMBER()

A user clicks two campaigns in the same session. Without deduplication they appear as a lead in both — inflating counts and distorting CPL.

CORRECT — First-touch attribution deduplication
WITH first_touch AS (
    SELECT
        user_id,
        campaign_id,
        ROW_NUMBER() OVER (
            PARTITION BY user_id      ← per person
            ORDER BY timestamp ASC    ← earliest click wins
        ) AS touch_rank
    FROM click_events
),
attributed_lead AS (
    SELECT user_id, campaign_id
    FROM first_touch
    WHERE touch_rank = 1        ← one campaign per user
)

SELECT
    al.campaign_id,
    COUNT(DISTINCT l.user_id) AS unique_leads
FROM lead_events l
INNER JOIN attributed_lead al ON l.user_id = al.user_id
GROUP BY 1
Result — u_001 counted once, in the right campaign
camp_77: 298 unique leads  ← u_001 attributed here (first touch)
camp_83: 271 unique leads  ← u_001 removed from this count
✅ Fix 5 — Safe Rollups Up the Hierarchy
CORRECT — Rolling up from clean daily grain
-- Weekly rollup
SELECT
    DATE_TRUNC('week', report_date)       AS week_start,
    campaign_id,
    SUM(impressions)                      AS impressions,
    SUM(spend)                            AS spend,
    SUM(leads)                            AS leads,
    SAFE_DIVIDE(SUM(spend), SUM(leads))  AS cpl,
    SAFE_DIVIDE(SUM(revenue), SUM(spend)) AS roas
FROM fact_daily_campaign_enriched
GROUP BY 1, 2;

-- Channel rollup (strip campaign, aggregate up)
SELECT
    DATE_TRUNC('month', report_date)      AS month_start,
    channel,
    SUM(spend)                            AS spend,
    SUM(leads)                            AS leads,
    SAFE_DIVIDE(SUM(spend), SUM(leads))  AS cpl
FROM fact_daily_campaign_enriched
GROUP BY 1, 2;
The Mental Model
Raw eventsmillions of rows, immutable, never query directly
↓ GROUP BY user_id + campaign_id
User-campaign CTEsone row per person per campaign — safe to join
↓ GROUP BY date + campaign_id
fact_daily_campaignone row per day per campaign — the core fact table
↓ GROUP BY week / month / channel
Dashboard rollupssmall, fast, correct — what the UI actually queries
The Rule
Every time you skip a step in that chain and jump directly from raw events to a rollup, you're gambling on grain integrity. SQL won't warn you. The numbers will just be wrong.

The Revenue Lag Problem

ROAS is the most commonly mis-measured metric in marketing data because revenue and spend live on different timelines.

The lag in raw data
Jan spend:  £4,800  booked immediately
Jan rev:    £2,249  only 9 deals closed in-month

Feb rev:    £3,229  13 more deals from Jan leads close late
                    (avg sales cycle = 18 days)

-- ROAS measured in January only: 0.47x  ← looks like a disaster
-- ROAS at 60-day window:          1.14x  ← actual picture
SQL — Windowed ROAS with configurable attribution window
WITH campaign_spend AS (
    SELECT campaign_id, SUM(spend) AS total_spend,
           MIN(report_date) AS campaign_start
    FROM fact_daily_campaign
    GROUP BY campaign_id
),
windowed_revenue AS (
    SELECT
        l.campaign_id,
        SUM(d.revenue) AS revenue_30d,
        COUNT(d.deal_id) AS deals_30d
    FROM lead_events l
    INNER JOIN deals d ON l.user_id = d.user_id
    WHERE
        -- Only count revenue within 30 days of the lead
        d.close_date BETWEEN l.submitted_at
                     AND DATE_ADD(l.submitted_at, INTERVAL 30 DAY)
    GROUP BY l.campaign_id
)

SELECT
    cs.campaign_id,
    cs.total_spend,
    wr.revenue_30d,
    wr.deals_30d,
    SAFE_DIVIDE(wr.revenue_30d, cs.total_spend) AS roas_30d
FROM campaign_spend cs
LEFT JOIN windowed_revenue wr ON cs.campaign_id = wr.campaign_id
M 03

Attribution — Pick One and Stick to It

The same journey produces four different stories depending on your model
User Journey
Jan 3 → organic social · Jan 7 → paid search · Jan 9 → email · Jan 11 → display retargeting · Jan 12 → buys £300
Four Models, Four Realities
First-Touch
All credit to Social. Paid Search, Email, Display get nothing.
Good for: brand awareness measurement
Last-Touch
All credit to Display. The top-of-funnel channels look worthless.
Good for: direct response campaigns
Linear
£75 to each channel. Equal split across all touches.
Good for: multi-touch journey analysis
Time-Decay
Social £18, Search £52, Email £89, Display £141.
Good for: long B2B sales cycles
The Operational Consequence
⚠ Real Business Impact
If you run last-touch attribution, your Social team looks useless and your Display team looks like heroes. You cut Social budget. Acquisition collapses — nobody was ever discovering you in the first place. The model was hiding the top-of-funnel contribution the entire time.
SQL — Time-Decay Attribution
Time-decay credit calculation
WITH touches AS (
    SELECT
        user_id,
        channel,
        campaign_id,
        timestamp,
        -- Days before conversion (0 = day of purchase)
        DATE_DIFF(
            conversion_date,
            DATE(timestamp),
            DAY
        )                        AS days_before_conv
    FROM click_events
    INNER JOIN conversions USING (user_id)
),
decay_weights AS (
    SELECT
        user_id, channel, campaign_id,
        -- Half-life decay: each day back = 0.5x less credit
        POW(0.5, days_before_conv / 7.0) AS weight
    FROM touches
),
normalised AS (
    SELECT
        user_id, channel, campaign_id,
        weight / SUM(weight) OVER (PARTITION BY user_id) AS credit_share
    FROM decay_weights
)

SELECT
    n.channel,
    n.campaign_id,
    SUM(n.credit_share * c.revenue) AS attributed_revenue
FROM normalised n
INNER JOIN conversions c USING (user_id)
GROUP BY 1, 2
M 04

Time — When the Same Number Means Different Things

UTC, timezones, and the week-start convention that rewrites history
User Journey
A campaign runs over a weekend. A user submits a lead at 23:45 Pacific Time on Sunday Jan 12. Depending on your timezone convention, that lead appears on Sunday or Monday.
The Timezone Split
Same event, two different "days" depending on storage convention
User submits form at 23:45 PT on Sunday Jan 12
→ UTC equivalent: 07:45 Monday Jan 13

Dashboard A (stores local US time):  lead on Sunday 12th
Dashboard B (stores UTC):            lead on Monday 13th

Week-on-week Sunday comparison:
  Dashboard A: 47 leads
  Dashboard B: 39 leads  ← 8 leads silently moved to Monday

Nobody changed the data. The timezone convention changed the story.
SQL — Correct Timezone Handling
UTC ingest + display timezone as derived field
-- At ingest: always store UTC
INSERT INTO lead_events (user_id, submitted_at_utc, ...)
VALUES (
    'u_001',
    TIMESTAMP('2025-01-13 07:45:00'),  ← UTC stored
    ...
);

-- At query time: derive local display fields
SELECT
    user_id,
    submitted_at_utc,
    DATETIME(submitted_at_utc, 'America/Los_Angeles') AS submitted_at_pt,
    DATE(DATETIME(submitted_at_utc, 'America/Los_Angeles')) AS report_date_pt,
    DATE(submitted_at_utc)                                  AS report_date_utc
FROM lead_events

-- Lock your reporting timezone in a config table
-- NEVER compute report_date inline in 47 different places
Calendar Day vs Rolling 24h
Same question, two valid but different answers
Question: "How many leads today?" asked at 14:00 UTC Jan 13

Calendar day:  leads from 00:00–14:00 Jan 13    = 31
Rolling 24h:   leads from 14:00 Jan 12–14:00 13 = 58

-- SQL for rolling 24h
SELECT COUNT(*) AS leads_rolling_24h
FROM lead_events
WHERE submitted_at_utc >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 24 HOUR)

-- SQL for calendar day
SELECT COUNT(*) AS leads_today
FROM lead_events
WHERE DATE(submitted_at_utc, 'Europe/London') = CURRENT_DATE('Europe/London')

-- Both are "correct." They mean completely different things.
-- Lock the definition before you build the chart.
M 05

Data Quality — Catching Lies Before They Reach a Stakeholder

Impossible values, bot traffic, test records, and distribution drift
User Journey
A bot farm hits your landing page. A developer tests a form. A pixel misfires and logs 9,847 clicks from a campaign that reached 12,600 people. All of this arrives in your pipeline looking like real data.
Impossible Values — Hard Reject Rules
The anomaly in raw data
Normal day:
  impressions: 12,400  │  clicks: 310    │  CTR: 2.5%

Anomaly day:
  impressions: 12,600  │  clicks: 9,847  │  CTR: 78.1%  ← impossible
SQL — Validation layer at ingest
CREATE VIEW validated_daily_campaign AS
SELECT
    *,
    CASE
        WHEN clicks > impressions
            THEN 'HARD_REJECT: clicks exceed impressions'
        WHEN spend < 0
            THEN 'HARD_REJECT: negative spend'
        WHEN SAFE_DIVIDE(clicks, impressions) > 0.20
             AND channel = 'display'
            THEN 'FLAG: CTR exceeds 20% on display'
        WHEN clicks > 500 AND leads = 0
            THEN 'FLAG: high clicks with zero conversions (bot pattern)'
        ELSE 'OK'
    END AS quality_flag
FROM raw_daily_campaign;

-- Dashboard queries only consume rows where quality_flag = 'OK'
-- Rejected rows land in a monitoring table for review
The Test Campaign Problem
Contaminated lead table
lead_id │ email                   │ campaign_id │ quality_flag
l_001   │ real.customer@gmail.com │ camp_77     │ OK
l_002   │ test@ourcompany.com     │ camp_77     │ INTERNAL_TEST
l_003   │ qa_bot_42@test.io       │ camp_77     │ QA_AUTOMATION
SQL — Documented exclusion rules at the model layer
CREATE VIEW clean_lead_events AS
SELECT *
FROM lead_events
WHERE
    -- Exclude internal test submissions
    email NOT LIKE '%@ourcompany.com'
    -- Exclude QA automation
    AND email NOT LIKE '%@test.io'
    -- Exclude known bot domains (maintained in ref table)
    AND SPLIT(email, '@')[OFFSET(1)] NOT IN (
        SELECT domain FROM ref_known_bot_domains
    )
    -- Flag must be clean
    AND is_test = FALSE
    AND is_internal = FALSE;

-- Document this view. Every exclusion rule here must have a
-- corresponding entry in the known_exclusions changelog.
Rule
Never silently drop records. Every exclusion must be documented and the excluded records must be visible in a monitoring table — otherwise you can't tell the difference between "excluded for a known reason" and "missing because the pipeline broke."
M 06

Visualising Large Datasets Without Lying

Aggregate first, chart second — the golden layout
User Journey
90 days of raw daily leads — noisy as hell. Weekends collapse, Mondays spike, bank holidays zero out. A stakeholder asks "are leads trending up or down?" You need to answer honestly without the noise obscuring the signal.
Rolling Averages — SQL
7-day rolling average to smooth noisy daily signal
SELECT
    report_date,
    leads                                            AS leads_raw,
    AVG(leads) OVER (
        ORDER BY report_date
        ROWS BETWEEN 6 PRECEDING AND CURRENT ROW  ← 7-day window
    )                                                AS leads_7d_avg,
    AVG(leads) OVER (
        ORDER BY report_date
        ROWS BETWEEN 27 PRECEDING AND CURRENT ROW ← 28-day window
    )                                                AS leads_28d_avg
FROM fact_leads_daily
ORDER BY report_date
The Golden Layout Pattern
Query architecture for each dashboard layer
-- Layer 1: Top-line KPI  (the answer)
SELECT
    SUM(leads)                                         AS total_leads,
    SAFE_DIVIDE(SUM(leads) - LAG(SUM(leads))
        OVER(ORDER BY month), LAG(SUM(leads))
        OVER(ORDER BY month))                         AS mom_change
FROM fact_leads_daily
WHERE report_date >= DATE_TRUNC(CURRENT_DATE(), MONTH);

-- Layer 2: Trend chart  (the story)
-- Only 5 lines max — aggregate by channel, not campaign
SELECT report_date, channel, SUM(leads) AS leads
FROM fact_leads_daily
JOIN dim_campaign USING (campaign_id)
GROUP BY 1, 2;

-- Layer 3: Drill-down table  (the proof)
-- All 847 campaigns, filterable, sortable, paginated
SELECT
    campaign_id, campaign_name, channel,
    SUM(leads) AS leads,
    SAFE_DIVIDE(SUM(spend), SUM(leads)) AS cpl
FROM fact_daily_campaign_enriched
WHERE report_date BETWEEN @start_date AND @end_date
GROUP BY 1, 2, 3
ORDER BY leads DESC
LIMIT 100;  ← paginate server-side
The User Journey Through the UI
1. KPI tile — "are we up or down?"  →  2. Trend chart — "when did it change?"  →  3. Filter by channel — "which channel drove it?"  →  4. Sort table by CPL — "which campaigns are efficient?"
M 07

Pre-Publish Checklist — The Real Failure Modes

Each item corresponds to a specific, documented way dashboards break trust
Checklist
  • Metrics reconcile with source-of-truth You ship a dashboard showing £1.2M revenue. Finance's report says £980k. You lose all credibility instantly. Always cross-check against the agreed source of truth within expected tolerance before any stakeholder sees it.
  • Date range and timezone visible on screen Stakeholder screenshots your chart for a board deck. Context disappears. Nobody knows it's only 14 days of data in Pacific Time. Always render the date range and timezone label on the chart itself, not just in a filter.
  • Filters update all dependent visuals User filters to "UK only." The trend chart updates. The KPI tile doesn't. They make a £2M UK budget decision based on global numbers. Every interactive filter must be wired to every chart that could be affected.
  • Empty states handled gracefully No data for selected segment returns a blank white box. Stakeholder assumes the dashboard is broken and stops trusting it. Always render a clear "No data for this filter combination" message — never a silent void.
  • Fast on large date range Someone selects "all time." Browser tab hangs for 40 seconds. They never come back. Pre-aggregate in the pipeline so the dashboard query always hits small, fast tables regardless of the date range selected.
  • Exclusion rules documented and visible Someone asks "why does your lead count differ from Salesforce?" The answer is test records and bot traffic. If you can't point to a documented exclusion log, you look like you're hiding something — even if you aren't.
  • Attribution model labelled on every ROAS/CPL figure Last-touch ROAS of 3.2x and linear ROAS of 1.8x are both "correct." Presenting one without labelling the model is how marketing and finance end up in a room arguing about which number is real.
The Thread Connecting All Modules
Core Principle
Every module is really about the same thing. One real person took a journey, left a trail of data, and your job is to represent that trail honestly and efficiently — without letting technical artefacts (grain mismatches, timezone bugs, bot traffic, attribution choices) distort the story into something that never happened.
